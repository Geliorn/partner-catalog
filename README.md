# Partner Catalog (partner-catalog)

Версия 0.5.0 · Самодостаточный WordPress-плагин: каталог подрядчиков и сервис-провайдеров (интеграторы, дистрибьюторы, хостинги, облачные платформы и т.д.) с **полностью ручным** наполнением карточек через админку. Никакого коллектора/парсинга/внешнего API — в этом ключевое архитектурное отличие от `llm-agent-github-repos`. Не зависит от ACF/CPT UI — переносим на любой сайт копированием папки.

**Название раздела на сайте — «Сервисы»** (решение 2026-10-17): так подписаны меню, крошки, заголовок архива («AI-сервисы»), админка и блоки. Внутренние имена не менялись: тип записи `contractor`, таксономии `contractor_*`, префикс `pc_`. **Адреса** (тоже 2026-10-17): архив `/services/`, типы `/service-type/…`, специализации `/specialization/…`; старые `/contractors/…` и `/contractor-type/…` отдают 301 на новые с сохранением параметров (`PC_CPT::legacy_redirect()`), правила перезаписи сбрасываются один раз сами после обновления. В тексте ниже «подрядчик» и «поставщик» означают то же самое.

Проектный план и обоснование решений (референсы startpack.ru/workspace.ru, разбор полей, макеты) — `docs/partner-catalog-plan.md` в корне репозитория. Дизайн 0.5.0 (карточка, архивы A/B, страница поставщика, «Где попробовать») — согласованные макеты `docs/mockups/partner-catalog-v2/` (`archive-a.html`, `archive-b.html`, `single-c.html`, `recommended.html`). Этот файл — справочник по тому, что реально реализовано в коде.

## 1. Структура данных

### Тип записи (`class-pc-cpt.php`)

- **`contractor`** (Подрядчики) — публичный, с архивом (`/contractors/`), `show_in_rest`. Поддержка: `title`, `editor` (полное описание компании через `post_content`), `thumbnail` (логотип), `revisions`.

### Таксономии

- **`contractor_type`** — тип сервиса/партнёра. **Открытый список терминов, множественный выбор.** Это ключевой механизм универсальности плагина: чтобы добавить новый тип сервиса (хостинг, облачная платформа, что угодно ещё) — не нужно трогать код, достаточно завести новый термин через админку. Компания может одновременно быть, например, и интегратором, и дистрибьютором.
- **`contractor_specialization`** — специализация/платформы/технологии подрядчика (1С, Bitrix24, AWS, MCP/AI-агенты и т.д.). Множественный выбор, растущий тег-подобный список.

**`contractor_region` удалена в 0.4.0.** План (раздел 3) обосновывал её фильтром «локация» на workspace.ru — но это каталог **агентств**, а наш наполнился AI-сервисами и платформами, для которых «регион присутствия» бессмысленен (у агрегатора API его нет), и на практике в каждом фасете региона лежало 1–2 записи. Решение пользователя 2026-10-13. Уже проставленные термины остались в БД просто незарегистрированными — при желании удаляются руками.

Роль «ещё одной оси фильтрации» вместо региона заняли **условия использования** — не таксономия, а чекбоксы (ниже): их ровно три, они не растут, и терминами они бы попали в облако тегов и навигацию, то есть ровно туда, откуда теги как раз вычищаются.

### Поля (`register_post_meta`, `show_in_rest: true` — Block Bindings в паттернах работают сразу)

Полный список — `PC_Meta_Fields::meta_keys()`:

| Meta-ключ | Назначение |
|---|---|
| `_pc_short_description` | Короткое описание (1–2 предложения) для карточки в архиве — отдельное поле, не `excerpt`, чтобы не путать с SEO-описанием |
| `_pc_website` | Сайт партнёра — никогда не выводится напрямую в разметку, см. раздел 4 |
| `_pc_price_type`, `_pc_price_value` | Универсальное поле цены — см. раздел 2 |
| `_pc_features` | Особенности сервиса, тезисно — каждая мысль с новой строки, на выходе немаркированный список (блок `partner-catalog/meta-list`, раздел 3) |
| `_pc_is_free`, `_pc_has_free_tier`, `_pc_has_trial` | **Условия использования** (0.4.0) — чекбоксы «Полностью бесплатный» / «Есть бесплатный тариф» / «Есть пробный период или демо». Хранятся как `'1'` либо отсутствуют. Выводятся блоком `partner-catalog/badges`, фильтруются в архиве (`?flag[]=free`). Список — `PC_Meta_Fields::flags()` |
| `_pc_promos` | **Промокоды** (0.5.0, несколько на запись) — поле-блокнот: промокоды через пустую строку, 1-я строка код, 2-я «что даёт», дальше необязательные `Для:`, `До:`, `Проверен:` (даты `ДД.ММ.ГГГГ`). Парсер `PC_Meta_Fields::promo_items()` отбрасывает просроченные. Блок `partner-catalog/promo`. Старые поля `_pc_promo_code/_description/_expires/_checked` при обновлении до 0.5.0 переносятся сюда первым блоком (`maybe_migrate()`), сами остаются в БД |
| `_pc_promo_live_until` | Вычисляемое, руками не правится: самая поздняя дата действия среди живых промокодов (`9999-12-31` для бессрочного). Нужно, чтобы фильтр «Есть промокод» оставался обычным `meta_query` |
| `_pc_fit` | **0.5.0** · «Подойдёт, если…» — продолжение фразы, выводится в шапке страницы, в таблице архива B и во врезке «Где попробовать» |
| `_pc_checked` | **0.5.0** · Дата «Условия проверены редакцией» — выводится внизу страницы; её обновление обнуляет сообщения о неточностях (раздел 7а) |
| `_pc_vpn` | **0.5.0** · Доступ из РФ: `no` — работает без VPN, `yes` — нужен VPN, пусто — не указано |
| `_pc_pay_card`, `_pc_pay_sbp`, `_pc_pay_invoice`, `_pc_pay_foreign`, `_pc_data_ru` | **0.5.0** · Оплата (карта РФ, СБП, счёт для юрлиц, только зарубежная карта) и «данные хранятся в РФ» — чекбоксы `'1'`/нет |
| `_pc_plat_web`, `_pc_plat_telegram`, `_pc_plat_api`, `_pc_plat_app`, `_pc_plat_selfhost` | **0.5.0** · Платформы — чекбоксы. Из оплаты/VPN/платформ собираются «ключевые факты» карточки (`PC_Meta_Fields::facts()`) и фильтры архива |
| `_pc_tariffs` | **0.5.0** · Тарифы, по строке на тариф: «название \| цена \| что входит» — таблица «Тарифы» на странице |
| `_pc_price_sort` | Вычисляемое: число для сортировки «сначала дешевле» (бесплатно = 0, «по запросу» — в конец) |
| `_pc_priority` | **0.5.0** · Приоритет 0–100 во врезке «Где попробовать» (раздел 7б); 0 — не показывать |
| `_pc_faq` | **Вопросы и ответы** (0.4.0) — блоки через пустую строку: первая строка вопрос, остальные ответ. Парсер — `PC_Meta_Fields::faq_items()`, вывод — блок `partner-catalog/faq`, те же пары идут в разметку FAQPage (раздел 7) |
| `_pc_utm_override` | Ручные UTM-параметры для конкретной записи — см. раздел 4 |

`_pc_team_size` (размер команды) **удалён в 0.4.0** вместе с регионом, по той же причине: для сервиса/платформы это не характеристика, план сам отмечал поле как бессмысленное для облачной платформы.

**Удалены в 0.5.0**: «Ключевые клиенты» (`_pc_clients`) — из метабокса, паттерна, CSV-импорта и промпта AI-описаний; значения остались в БД.

Также **удалены в 0.4.0**: контакты (`_pc_phone`, `_pc_email`, `_pc_telegram`, `_pc_vk`), партнёрства (`_pc_partnership`) и год основания (`_pc_founded_year`) — из метабокса, CSV-импорта, паттернов, schema.org (`foundingDate`) и промпта AI-описаний. Путь посетителя к сервису — отслеживаемая кнопка «Перейти на сайт», а эти поля не заполнялись достаточно ровно, чтобы занимать место на странице. Уже сохранённые значения остались в БД, но нигде не выводятся.

**Полное описание** (`post_content`) — обычный Gutenberg-контент, редактируется в стандартном редакторе записи, не отдельное meta-поле. Так работает `core/post-content` в single-паттерне.

## 2. Цена — универсальное поле (`_pc_price_type` + `_pc_price_value`)

Разные типы сервисов озвучивают цену по-разному (интегратор — «от», хостинг — тариф/подписка, разработка под ключ — фиксированная сумма, консалтинг — почасовая ставка). Поэтому цена — это **тип (select) + значение (текст)**, а не один свободный текст:

| Тип (`_pc_price_type`) | Как выводится |
|---|---|
| `free` | «Бесплатно» (значение не нужно) |
| `subscription` | «от {value} ₽/мес» (с 0.5.0 с «от») — суффикс добавляется только к чистому числу; если в значении уже есть своя единица («990 ₽/мес за место»), выводится как есть |
| `usage` | «{value}» как есть (например «120 ₽ за 1М токенов»); без значения — «Оплата по потреблению» |
| `from` | «от {value} ₽» |
| `range` | «{value} ₽» (значение уже вида «150 000 – 500 000») |
| `fixed` | «{value} ₽», под ценой серым «за проект» (`PC_Meta_Fields::price_note()`) |
| `hourly` | «{value} ₽/час» |
| `on_request` | «По запросу» (значение не нужно) |

`free`/`subscription`/`usage` добавлены в 0.4.0: исходные пять типов были списаны с интегратора (проектная работа), а AI-сервис почти никогда так не продаётся — это месячный тариф, оплата по токенам или бесплатно. Без них самый частый в этом каталоге случай приходилось вписывать руками в поле значения, то есть ровно тот разнобой, ради борьбы с которым select и существует.

В meta-боксе под полем — подсказка с примерами по каждому типу. Единицы измерения вроде «/мес» дописываются прямо в значении — форматтер их не навязывает (см. `blocks/price/render.php`).

Форматирование — не `core/post-meta` binding (он не умеет условной логики), а `PC_Meta_Fields::price_text()` / `price_note()`: ими пользуются блок `partner-catalog/price`, карточка, таблица и шапка страницы, чтобы везде было одно и то же. Если отмечен «бесплатный тариф», под ценой добавляется «есть бесплатный тариф».

## 3. Динамические блоки (`class-pc-blocks.php`, `blocks/`)

`core/post-meta` binding умеет только отдать значение поля как есть — не может превратить многострочный текст в список или применить условие по типу цены. Плюс блоки, заменяющие сторонние плагины (раздел 3а). Отсюда набор маленьких серверных блоков:

| Блок | Назначение |
|---|---|
| `partner-catalog/meta-list` | Читает multiline meta-поле (`_pc_features`), разбивает по строкам. `style`: `bullet`, `checks` (галочки колонками — «Особенности» на странице) или `badges`. Необязательный `heading` выводится только если список не пуст |
| `partner-catalog/price` | Цена одной строкой, раздел 2 |
| `partner-catalog/rating` | **0.5.0** · «Оценки посетителей»: средняя со звёздами, полоски по 5 критериям и форма «Пользовались? Оцените» (SVG-звёзды вместо сердечек), раздел 3б. `interactive:false` — компактная строка «4,6 ★★★★★ (128)» |
| `partner-catalog/related-posts` | **0.5.0** · «Альтернативы» — мини-карточки (лого, тип, звёзды, 2 факта, цена, «Подробнее →» у нижнего края) |
| `partner-catalog/contractor-filters` | Фильтры боковой колонки архива A, раздел 5а. На телефоне — выдвижная панель |
| `partner-catalog/badges` | Пилюли: «Часто выбирают» (топ-3 по переходам за 30 дней, `PC_Stats::popular_ids()`), «Бесплатный», «Бесплатный тариф», «Пробный период» — **не больше 2** (атрибут `max`). Пилюли промокода с 0.5.0 нет |
| `partner-catalog/promo` | **0.5.0** · «Промокоды»: каждый живой код «билетом» — для кого, что даёт, «Проверен …», срок; код размыт до клика «Показать код», клик копирует его и шлёт цель Метрики `partner_promo_copy`. Нет живых кодов — блока нет |
| `partner-catalog/card` | **0.5.0** · Карточка архива A (`PC_Render::card()`): лого, название, тип и специализация строкой, звёзды, ≤2 пилюли, описание, 3 факта, цена и **только «Подробнее →»** — кнопки «На сайт» и купона промокода на карточке нет, переход идёт через страницу поставщика |
| `partner-catalog/archive-head` | **0.5.0** · Хлебные крошки + H1 «Поставщики AI-сервисов» + подзаголовок; на странице типа/специализации — название и описание термина. Заменил `core/query-title` («Archives: …») |
| `partner-catalog/archive-toolbar` | **0.5.0** · Над сеткой A: число найденных, выбранные фильтры чипами, сортировка, «плитка / список» (запоминается в браузере), кнопка «Фильтры · N» на телефоне |
| `partner-catalog/archive-table` | **0.5.0** · Архив B целиком: вкладки по типам, быстрые фильтры, таблица (рейтинг, без VPN, оплата из РФ, платформы, цена, «Подробнее →») с сортировкой по клику на заголовок, пагинация. Работает поверх основного запроса архива |
| `partner-catalog/hero` | **0.5.0** · Шапка страницы поставщика во всю ширину: крошки, лого, название, «Подойдёт, если…», «Перейти на сайт» (через `/out/{id}/`), плитки «Посетители / Цена / Сильная сторона» |
| `partner-catalog/tariffs` | **0.5.0** · Таблица «Тарифы» из `_pc_tariffs` |
| `partner-catalog/verify` | **0.5.0** · «Условия проверены редакцией ДАТА · Сообщить о неточности», раздел 7а |
| `partner-catalog/recommended` | **0.5.0** · «Где попробовать» для ручной вставки в статью, раздел 7б |
| `partner-catalog/faq` | **0.4.0** · Вопросы/ответы из `_pc_faq` на нативных `<details>/<summary>` — раскрывается без JS, доступен с клавиатуры, ищется браузерным Ctrl+F; `viewScript` не нужен вовсе |

Все — без сборки (JS через `wp.blocks.registerBlockType`, не собранный React/JSX), рендер — чистый PHP (`render.php`), поэтому корректно работают внутри Query Loop (пересчитываются на каждый элемент цикла, как `core/post-title`) — в отличие от шорткода, который резолвится один раз на всю страницу (см. известную находку про `[ratings]` в README `llm-agent-github-repos`, раздел 8б — та же причина, тот же класс проблемы, из-за которой рейтинг и похожие подрядчики тоже сделаны блоками, а не шорткодами).

### 3а. Свой рейтинг и «Похожие подрядчики» (`class-pc-ratings.php`, `class-pc-related.php`) — с версии 0.2.0

**Решение 2026-09-04** (одновременно с тем же изменением в `llm-agent-github-repos`): WP-PostRatings и Contextual Related Posts убраны из зависимостей — обе функции по объёму оказались достаточно маленькими, чтобы держать свой код было разумнее, чем тянуть два сторонних плагина на каждый из 20 сайтов сети. Filter Everything остался сторонним (раздел 5) — там объём для самостоятельной переделки несоразмерный.

- **Рейтинг.** Инкремент атомарным `UPDATE ... SET meta_value = meta_value + N` (не read-then-write — иначе одновременные голоса теряются), AJAX (`wp_ajax_pc_rate`), один голос с браузера через cookie `pc_voted_{id}` — без другой защиты от накрутки, тот же уровень простоты, что у счётчика кликов (раздел 4.2). Состав оценок переделан в 0.4.0, см. ниже.
- **Похожие подрядчики.** `get_posts()` с `tax_query` (`relation: OR`) по общим терминам `contractor_type` ИЛИ `contractor_specialization` — точнее, чем generic keyword-matching CRP, раз у записи уже есть две структурные оси похожести.
- Код **не переиспользуется** между `partner-catalog` и `llm-agent-github-repos` (дублирован) — оба плагина обязаны оставаться независимо переносимыми по отдельности.

### 3б. Оценки по критериям, без текста отзыва — с версии 0.4.0

Одна звёздочная оценка ничего не говорит о AI-сервисе: «цена» и «качество результата» — это как раз то, в чём мнения расходятся, а усреднение в одно число именно это и выбрасывает. Поэтому вместо одного балла — несколько критериев, каждый по своей 5-балльной шкале (`PC_Ratings::criteria()`, фильтр `pc_rating_criteria`, чтобы соседний сайт сети мог задать свой набор без форка):

> Качество результата · Цена и тарифы · Удобство использования · Поддержка · Стабильность и скорость

**Текста отзыва сознательно нет** (решение пользователя 2026-10-13): свободный текст — это персональные данные автора, а значит согласия, модерация и удаление по требованию, к чему сайт пока не готов. Это рейтинг-виджет, а не система отзывов; ничего из введённого посетителем, кроме баллов, не сохраняется.

Как хранится, на одного подрядчика:

| Ключ | Что |
|---|---|
| `_pc_rating_{критерий}_total` / `_pc_rating_{критерий}_count` | Сумма и число оценок по каждому критерию |
| `_pc_rating_total` / `_pc_rating_count` | **Общий** агрегат, где один голосующий даёт вклад, равный средней его собственных оценок — чтобы заполнивший два критерия не весил больше заполнившего пять. Ключи те же, что до 0.4.0, поэтому старые голоса остаются валидными, а `get_average()` означает то же самое |
| `_pc_rating_avg` | Тот же общий средний балл, закэшированный как сортируемое число |
| `_pc_rating_rank` | **0.5.0** · Ключ сортировки «по рейтингу»: средний балл, если оценок ≥ 3 (`PC_Ratings::MIN_VOTES`), иначе его сотая доля — записи с 1–2 оценками идут после остальных |

**Звёзды показываются всегда** (решение 2026-10-17): при любом числе оценок — настоящий балл, без оценок — 5 серых звёзд. Порог в 3 оценки влияет только на сортировку и на schema.org (раздел 7). Звёзды — SVG-глиф Material «star» с заливкой `#FBBC04`, как в сниппетах Google, с дробной заливкой каждой звезды (`PC_Render::stars()`).

Два неочевидных момента, оба — причина существования `_pc_rating_avg`:

1. Сортировка по рейтингу не может пересчитывать `total/count` построчно, а запись **без** этого meta-ключа молча выпала бы из отсортированной по meta выборки — поэтому ключ засеивается нулём каждой записи (`PC_Ratings::ensure_sort_meta()` на `save_post`, плюс однократный проход по уже существующим записям).
2. Голос отправляется **одним** запросом на все критерии (кнопка «Оценить»), а клик по звезде только выбирает балл. Иначе cookie-защита «один голос с браузера» срабатывала бы на первом же критерии и запирала посетителя на полузаполненной форме.

## 4. Аналитика и UTM-метки

Плагин не только показывает карточки, но и считает переходы/клики по каждой и размечает исходящие ссылки UTM-метками. Без защиты от фрода/ботов — простой внутренний дашборд, не CPA-платформа.

### 4.1. UTM — авто или вручную, с приоритетом override (`class-pc-links.php::build_final_url()`)

- **Авто (по умолчанию).** Настройки плагина задают шаблон: `utm_source`, `utm_medium`, `utm_campaign`/`utm_content` с токенами `{slug}` и `{contractor_type}`.
- **Вручную (опционально, на уровне записи).** Поле «Ручные UTM-параметры» (`_pc_utm_override`) в карточке подрядчика — строка вида `utm_source=vk&utm_medium=cpc`. Если заполнено — **полностью заменяет** автогенерацию для этой записи.
- Реальный URL партнёра (`_pc_website`) никогда не печатается в разметке напрямую — только через генератор.

### 4.2. Счётчик переходов/кликов (`class-pc-stats.php`)

Своя таблица `{prefix}pc_stats` (`contractor_id`, `event_type` — `view`/`click`, `stat_date`, `count`; уникальный ключ на все три, инкремент через `INSERT … ON DUPLICATE KEY UPDATE`):

- **`view`** — на каждый реальный показ `single-contractor` (`template_redirect`, без дедупликации по IP/сессии — намеренно просто).
- **`click`** — все ссылки «на сайт партнёра» в паттернах ведут не на реальный сайт напрямую, а на собственный редирект-эндпоинт `/out/{id}/` (`class-pc-links.php`). Обработчик: проверка записи → инкремент клика → подстановка UTM (раздел 4.1) → `wp_redirect()` (302). Один эндпоинт закрывает обе задачи.

Кнопка на сайте партнёра биндится не на реальное meta-поле, а на **виртуальный** `_pc_outbound_url` — оно не хранится в БД, значение подставляется на лету через short-circuit фильтра `get_post_metadata` (нужно, чтобы Block Bindings внутри Query Loop могли получить готовый URL редиректа для каждой карточки отдельно — то же ограничение шорткодов внутри цикла, что и в разделе 3).

### 4.3. Дашборд в админке (`class-pc-admin.php`, меню «Подрядчики → Аналитика»)

KPI (переходы, клики, конверсия %), график по дням (простой canvas без внешних библиотек — сознательно, чтобы не тянуть CDN-зависимость в `wp-admin`, см. `assets/js/pc-admin-dashboard.js`), таблица по подрядчикам, фильтры по типу/специализации/региону и по конкретной записи, диапазон дат.

### 4.4. Цели в Яндекс.Метрику (`assets/js/pc-analytics.js`)

ID счётчика — отдельное поле в настройках (не предполагается, что счётчик уже где-то программно доступен плагину). Две цели, обе no-op, если `ym` не определён или ID не задан:

- **`partner_profile_view`** — при загрузке страницы подрядчика.
- **`partner_click`** — по клику на ссылку с классом `pc-outbound-link` (только реальная кнопка «Перейти на сайт», не социальные ссылки — см. комментарий в `class-pc-patterns.php::bound_button()`).

## 5. Паттерны (`class-pc-patterns.php`)

Реализация макетов из `docs/mockups/partner-catalog-pattern-*.html` — **не копия** паттернов `llm-agent-github-repos`: там репозиторий со звёздами/языком/лицензией, здесь сервис со специализацией/ценой/условиями — разный состав данных, разная композиция.

| Паттерн | Что это |
|---|---|
| `partner-catalog/card` | Одна карточка — содержимое Post Template внутри Query Loop (блок `partner-catalog/card`). |
| `partner-catalog/archive-cards` | **Архив A**: шапка, фильтры в боковой колонке, панель над списком, сетка карточек (плитка/список), пагинация; `inherit:true`. |
| `partner-catalog/archive-table` | **Архив B**: шапка + блок `partner-catalog/archive-table`. |
| `partner-catalog/archive` | Слот, который используют шаблоны архива темы: содержит A или B в зависимости от настройки «Вид каталога» — переключение без Site Editor. |
| `partner-catalog/archive-grid` | Только сетка карточек с пагинацией — оставлен для шаблонов, сохранённых до 0.5.0. |
| `partner-catalog/single-layout` | **Страница поставщика** (макет C): шапка во всю ширину → О сервисе → Особенности → Тарифы → Промокоды → Оценки посетителей → Частые вопросы → «Проверено редакцией · Сообщить о неточности» → Альтернативы. Каждый блок с заголовком сам скрывается, если ему нечего показать. |

**Гейтинг по интеграциям** — блок рейтинга (`partner-catalog/rating`) и «Похожие подрядчики» (`partner-catalog/related-posts`) вставляются только если соответствующий тумблер в настройках включён (`PC_Settings::integration_enabled()`), проверяется на PHP-стороне в момент регистрации паттерна — тот же принцип, что в GitHub-плагине. Тумблеры больше не про «установлен ли сторонний плагин» (см. раздел 3а) — просто «включена ли фича».

**Патterns — только вставляемые заготовки.** Как и в GitHub-плагине: привязка паттернов к реальным шаблонам сайта (архив, single) — отдельный ручной шаг в Site Editor, не выполняется автоматически при регистрации.

### 5а. Фильтры и сортировка архива (`class-pc-filters.php`, `blocks/contractor-filters`)

Обычная GET-форма, без AJAX и сторонних скриптов (`view.js` только убирает лишний клик, автоотправляя форму на `change`; без JS работает кнопка «Применить»).

- **Сортировка** (`?sort=`) — `default` (новые сверху) · `rating` (по `_pc_rating_rank`) · `reviews` · `price` / `price_desc` (по `_pc_price_sort`) · `alpha`. С 0.5.0 select живёт в панели над списком (`archive-toolbar`) — отдельная GET-форма, которая передаёт все активные фильтры скрытыми полями; в архиве B сортировка — ссылки в заголовках таблицы.
- **Фасеты таксономий** (`?type[]=`, `?spec[]=`) — внутри группы OR, между группами AND. Фасет той таксономии, на архиве которой мы уже находимся, не показывается: URL сам и есть этот фильтр.
- **Флаги** (`?flag[]=`) — meta, не термины, три группы (`PC_Filters::flag_groups()`): «Доступ и оплата» (`no_vpn`, `pay_ru` — карта ИЛИ СБП, `invoice`, `data_ru`), «Условия» (`free`, `free_tier`, `trial`, `promo`), «Платформы» (`web`, `telegram`, `api`, `app`, `selfhost`). `promo` сравнивает `_pc_promo_live_until` с сегодняшней датой, поэтому истёкший промокод перестаёт попадать в фильтр сам. Старые ссылки с `free|free_tier|trial|promo` работают как раньше.
- В группе показывается до 6 вариантов, остальные под «Ещё N». На телефоне форма — выдвижная панель: галочки не отправляют форму сразу, «Готово» применяет всё вместе.
- Счётчики у каждой опции считаются в текущем контексте, **исключая собственный выбор** этой же группы — иначе второй чекбокс внутри группы показывал бы 0 (`PC_Filters::scoped_ids()`).

Про сортировку по рейтингу два подводных камня, оба зафиксированы в коде:

1. `'type' => 'NUMERIC'` в `meta_query` кастует к `SIGNED`, то есть **отбрасывает дробную часть** — 4,9 и 4,1 сортировались бы как одинаковые «4». Используется `DECIMAL(10,3)`.
2. Сортировка идёт по **именованному** клаузу (`pc_sort`), а не через `meta_key`, чтобы не столкнуться с клаузами флагов в том же `meta_query`.

## 6. Настройки (`class-pc-admin.php`, `class-pc-settings.php`)

Пункт меню «Подрядчики» (`pc-main`) + подпункты:

Тип сервиса — столбец `type` (пишется в таксономию `contractor_type`), специализация — `specialization`. Столбцы `phone`, `email`, `telegram`, `vk`, `partnership`, `founded_year` с 0.4.0 не поддерживаются и игнорируются, если остались в старом файле.

## 7. Разметка schema.org (`class-pc-schema.php`) — с версии 0.4.0

Единственное, чего не делал ни этот плагин, ни `llm-agent-github-repos`: `PC_SEO`/`LAGR_SEO` только вписывали meta description в Yoast/RankMath. Без JSON-LD собранный сайтом рейтинг не виден поисковику — то есть нет звёзд в сниппете, а это и есть практический смысл собирать оценки.

- Один `<script type="application/ld+json">` с `@graph`, а не несколько тегов: FAQ и сам сервис — разные сущности, и граф — это то, как они остаются связанными (`FAQPage.about` → `@id` сервиса), а не выглядят как два независимых документа на одном URL.
- `@type` записи — **всегда `Organization`** (решение 2026-10-15; ручное поле `_pc_schema_type` убрано). Раньше по умолчанию был `SoftwareApplication`, но Google показывает для него звёзды только при числовом `offers.price` — а у большинства записей цена «по запросу» или по потреблению, и они теряли сниппет целиком. `Organization` цены не требует, а сторонний каталог, оценивающий чужие компании, — не «самовосхваляющие отзывы», которые Google исключает. `LocalBusiness` не используется: он требует адреса. Тип и специализация идут в `keywords`.
- `url` — всегда страница каталога, которую эта разметка описывает; сайт партнёра идёт в `sameAs`. Иначе сущность заявляет, что она **и есть** внешний сайт.
- **Цены в разметке нет**: у `Organization` нет свойства `offers`, а `makesOffer` Google в сниппете не использует. Цена выводится только на странице.
- `aggregateRating` — только **от 3 оценок** (`PC_Ratings::MIN_VOTES`, с 0.5.0; звёзды на странице видны и раньше) **и при включённом рейтинге** в настройках: Google требует, чтобы оценка из разметки была видна на странице.
- Ожидания: звёзды возможны только в **Google** и на его усмотрение. **Яндекс** рейтинг из `aggregateRating` в сниппет не берёт. Расширенные результаты **FAQ** Google с 2023 года показывает только государственным и медицинским сайтам — `FAQPage` остаётся, но сниппета не даст.
- **Гейтится тумблером** `integration_schema`: полноценный SEO-плагин может уже отдавать свой граф для типа записи, а две конфликтующие схемы на одном URL хуже одной.

### 7а. «Сообщить о неточности» (`class-pc-reports.php`, блок `partner-catalog/verify`) — 0.5.0

Посетитель выбирает причину из списка (цена или тарифы · перестал работать без VPN · промокод не действует · сервис закрылся · другое) — **без текста**, поэтому никаких персональных данных. Счётчики по причинам — в `_pc_reports`, видны колонкой «Неточности» в списке поставщиков (число, при наведении — разбивка). Один отчёт с браузера в сутки (cookie). **Новая дата в «Условия проверены редакцией» обнуляет отчёты** — свежая проверка отвечает на старые сигналы.

### 7б. «Где попробовать» в статьях (`class-pc-recommend.php`) — 0.5.0

Врезка из 3 поставщиков: лого, название, пилюля типа, звёзды, «Подойдёт, если…», «Подробнее →». **Без цены и без пометки** (решение 2026-10-17). Ссылки ведут на страницу поставщика в каталоге, а не на его сайт — модуль переводит трафик статей в каталог.

- **Куда:** автоматически в записи типов из настройки (по умолчанию `post`), после абзаца, идущего за 2-м `<h2>`; если подзаголовков меньше — после 3-го абзаца; в совсем короткие статьи не вставляется. Если в статье стоит блок `partner-catalog/recommended`, автоматическая вставка для неё пропускается.
- **Кого:** только по ручному приоритету `_pc_priority` (0–100, решение 2026-10-17 — без учёта тем статьи). Сервер рендерит пул из 8 лучших по приоритету (кэш — transient на час, сбрасывается при сохранении поставщика), первые 3 видимы.
- **Ротация:** `assets/js/pc-recommend.js` заново выбирает 3 из пула взвешенной выборкой без повторов (Efraimidis–Spirakis, `u^(1/вес)`): высокий приоритет показывается чаще, но не забирает все места. Выбор в браузере — чтобы полностраничный кэш не «замораживал» один показ для всех; без JS виден порядок по приоритету.
- **Важно:** если за место или приоритет в модуле поставщик платит, по ст. 18.1 закона «О рекламе» может понадобиться маркировка (пометка «Реклама», рекламодатель, erid). Сейчас пометки нет по решению владельца; добавить её — одна строка в `PC_Recommend::render()`.

## 9. Известные ограничения

- Счётчики `view`/`click` не защищены от повторных заходов/ботов — если это станет проблемой (например, разброс конверсии из-за самих поисковых роботов), потребуется отдельная доработка (исключение известных User-Agent, троттлинг по IP/сессии).
- UTM-override (`_pc_utm_override`) ожидает формат query-строки (`key=value&key2=value2`) — при опечатке в формате `parse_str()` либо ничего не распарсит, либо распарсит не то, что имелось в виду; валидации формата в meta-боксе нет.
- Дашборд аналитики не пагинирует таблицу «по подрядчикам» — при большом количестве записей и активности стоит добавить лимит/постраничность (сейчас жёстко ограничено 30 строками через `LIMIT`, без навигации по остальным).
- **Оценки без текста отзыва — это решение, а не недоделка** (раздел 3б): отзывы с текстом требуют работы по персональным данным, к которой сайт пока не готов. Если её делать, смысл имеет и сортировка «сначала негативные/положительные» с референса, но это уже другая сущность (комментарии), а не расширение этого виджета.
- **Термины удалённой таксономии `contractor_region` остаются в БД** — код их просто больше не регистрирует, автоудаления нет сознательно (удалять чужие данные при обновлении плагина — хуже, чем оставить невидимый мусор). Если они не нужны, удалить их придётся вручную до обновления, пока таксономия ещё зарегистрирована.
- «Показать код» промокода отправляет только цель Метрики `partner_promo_copy`, в собственную статистику (`wp_pc_stats`) не пишется. Отдельный тип события (например `promo`) — доработка на будущее, `event_type` под него уже подходит по длине.
- Показы врезки «Где попробовать» не считаются; переходы из неё видны как просмотры страниц поставщиков.
- Чекбокс «Сравнить» в макетах v2 есть, в коде — нет: страницы сравнения пока нет (раздел 8).
